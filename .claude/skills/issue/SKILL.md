# Issue

リポジトリは `zono0013/codegen`。`gh issue create -R zono0013/codegen` で立てる。

## 粒度の切り方

- **1 つの Issue = 1 つの PR で閉じられる単位。** 原因が違うものは分ける。同じ原因で複数の症状が出ているなら 1 つにまとめる
  - 例: 「整数の @pk で Entity がコンパイルできない」と「整数の path パラメータで Handler がコンパイルできない」は、テンプレートも原因も違うので別の Issue
  - 例: path の int64 と query の uint64 は、同じ「型に合わせて読んでいない」が原因なので 1 つ
- **バグ・機能・ドキュメントを混ぜない**
- 試用（別のアプリで codegen を使ってみる）で見つかった問題は、全部を見つけ終えてから、まとめて分けて立てる。直しながら立てると、粒度がぶれる
- 重い順（コンパイルできない → 動きがおかしい → 使いにくい → ドキュメント）に立てて、その順に直す

## 本文の型

日本語で書く。

```markdown
## 何が起きたか（バグ） / 背景（機能・ドキュメント）

<再現する入力（proto など）と、出力・エラーをそのまま貼る>

## 期待する動き / 方針

<どうなるべきか。決まっていない点は「決めること」として書く>

## やること

- [ ] <実装>
- [ ] <テスト（どこで何を確かめるか）>
- [ ] <docs の更新（spec.md など）>
```

- 再現は、最小の proto とエラーメッセージで書く。手元のパスや、ほかのリポジトリの中身は書かない
- 「やること」には、直したことをどう確かめるかを必ず入れる

## ラベル

| ラベル | 使うとき |
| --- | --- |
| `bug` | 生成物が壊れる、仕様どおりに動かない |
| `enhancement` | 機能の追加・変更 |
| `documentation` | docs だけの変更 |
| `dependencies` / `security` | 依存の更新・脆弱性（ふつうは Renovate が付ける） |

## 立てた後

- 既にある Issue と重なっていないかを `gh issue list -R zono0013/codegen` で確かめる。重なっていたら、新しく立てずに既存の Issue にコメントする
- 方針が変わって不要になった Issue は、理由をコメントして `--reason "not planned"` で閉じる（閉じる前にユーザーに確かめる）
